# tests/files/enc — content-coding fixtures (br / zstd / gzip)

Pinned inputs for the brotli and zstd ctypes decoders (`Scripts/_mcp_brotli.py`,
`Scripts/_mcp_zstd.py`) and the gzip/content-coding paths of the Chrome client
(roadmap R-0044, feature plan Step 3 [D7]). They are read by path through
`H.repo_path("tests", "files", "enc", ...)`, the same way `tests/test_py_deps.py`
reads `tests/files/html/tf_bing_serp.html`.

**They were produced ONCE with the `brotli`, `zstd` and `gzip` command-line
tools and are never regenerated by a test.** The CLIs are the oracle: a test
compares what the module under test decodes against the plain original that the
CLI compressed, never against something the module itself produced. Regenerating
a fixture from the code under test would make the pin agree with whatever the
code does.

Every plain original follows the `tf` rule of `tests/files/README.md`: its text
contains no real project symbol, so a repo-wide search never lands here.

## Exact commands

Run from `tests/files/enc/`; `$T` is a scratch directory under `.claude/tmp/`.

```sh
# tf_page.html: written by hand.

# tf_text_1m.txt: 16384 fixed-width lines of 64 bytes = 1048576 bytes.
# seq writes stdout; zstd -o captures it, zstd -d -o writes the original.
seq -f "tf-enc line %05g: the quick brown fox jumps over the lazy dog." 1 16384 \
    | zstd -q -o $T/text.stdin.zst
zstd -q -d $T/text.stdin.zst -o tf_text_1m.txt

# tf_empty.txt
touch tf_empty.txt

# Path-based encodings of the three originals.
for f in tf_page.html tf_text_1m.txt tf_empty.txt; do
    brotli -q 11 -o $f.br $f
    zstd -q -19 $f -o $f.zst
    gzip -9 -n -k $f
done

# multi-frame.zst: one frame per 256 KiB part, concatenated by -o.
split -b 262144 tf_text_1m.txt $T/part-
zstd -q -f -3 $T/part-aa $T/part-ab $T/part-ac $T/part-ad -o multi-frame.zst

# Bombs.
dd if=/dev/zero of=$T/zeros-128m.bin bs=1048576 count=128
brotli -q 11 -o bomb.br $T/zeros-128m.bin
zstd -q -3 $T/zeros-128m.bin -o bomb.zst

# Truncated streams: a byte prefix of the page encodings.
cp tf_page.html.br truncated.br;   truncate -s 430 truncated.br
cp tf_page.html.zst truncated.zst; truncate -s 561 truncated.zst

# window-27.zst: FROM STDIN (R2-M1), literally the plan's recipe.
zstd --long=27 -c < tf_page.html > window-27.zst

# gzip-x3.gz: gzip three times (-n: no name, no mtime -> reproducible bytes).
cp tf_page.html $T/x3;  gzip -9 -n $T/x3
mv $T/x3.gz $T/x3l1;    gzip -9 -n $T/x3l1
mv $T/x3l1.gz $T/x3l2;  gzip -9 -n $T/x3l2
cp $T/x3l2.gz gzip-x3.gz

# gzip-members-bomb.gz: 72 members, each 1 MiB of zeros, concatenated by -o.
dd if=/dev/zero of=$T/zeros-1m.bin bs=1048576 count=1
zstd -q -f --format=gzip -9 $T/zeros-1m.bin (x72, same path) -o gzip-members-bomb.gz
```

### Why window-27.zst is compressed from stdin

Given a file path, the zstd CLI knows the source size and shrinks the window to
fit it, so a 2 KiB input compressed by path would carry a tiny window (compare
`tf_page.html.zst`, whose window is 2152 bytes). From stdin the size is unknown
and `--long=27` is honoured as written. zstd 1.5.7 did NOT shrink it, so the
small primary input was enough and the >8 MiB fallback input was not needed.

Frame header read back with `xxd -l 8 window-27.zst`:

```
00000000: 28b5 2ffd 0488 5d24
```

- bytes 0-3 `28 b5 2f fd`: zstd magic;
- byte 4, Frame_Header_Descriptor `0x04`: Content_Checksum_flag set,
  Single_Segment_flag 0 (so a Window_Descriptor follows), no Frame_Content_Size;
- byte 5, **Window_Descriptor `0x88`**: Exponent `0x88 >> 3` = 17, Mantissa 0;
- **windowLog = 10 + (0x88 >> 3) = 27** -> window 2^27 = 134217728 bytes (128 MiB),
  which `zstd -l -v` confirms ("Window Size: 128 MiB (134217728 B)").

27 > `ZSTD_WINDOW_LOG_MAX` (23), so a decoder configured with
`ZSTD_d_windowLogMax` 23 refuses the frame. The zstd CLI itself decodes it
(its default limit is 27); `zstd -d -c --long=27 window-27.zst | cmp - tf_page.html`
passes, so the frame is otherwise valid and the refusal is the window alone.

For comparison, `bomb.zst` reads `28b5 2ffd 8458 ...`: FHD `0x84`, Window_Descriptor
`0x58` -> windowLog 10 + 11 = 21, under the limit.

### Deviations from "use the CLI named after the format"

- `gzip-members-bomb.gz` was written by `zstd --format=gzip` (zlib deflate), not by
  the `gzip` CLI. Apple gzip has no `-o`; concatenating 72 of its members needs a
  shell redirect, while zstd concatenates multiple inputs into one `-o` file.
  The result is plain RFC 1952 members, checked with the `gzip` CLI:
  `gzip -dc gzip-members-bomb.gz | wc -c` prints `75497472` (72 x 1048576), and the
  file is exactly 72 x 1051 bytes, the size of one such member.
- `tf_text_1m.txt` was produced by piping `seq` into `zstd -o` and decoding it back
  with `zstd -d -o`, so no shell redirect writes a text file.

## Verification (run at production time)

```sh
for f in tf_page.html tf_text_1m.txt tf_empty.txt; do
    brotli -d -c $f.br  | cmp - $f
    zstd -d -c   $f.zst | cmp - $f
    gzip -dc     $f.gz  | cmp - $f
done
zstd -d -c multi-frame.zst | cmp - tf_text_1m.txt    # zstd -l: 4 frames
brotli -d -c bomb.br | cmp - $T/zeros-128m.bin
zstd -d -c bomb.zst  | cmp - $T/zeros-128m.bin
brotli -d -c truncated.br  -> exit 1
zstd -d -c truncated.zst   -> exit 1
zstd -d -c --long=27 window-27.zst | cmp - tf_page.html
gzip -dc gzip-x3.gz | gzip -dc | gzip -dc | cmp - tf_page.html
gzip -dc gzip-members-bomb.gz | wc -c                 # 75497472
```

All passed.
